## 우선순위별 과제

### P0 — 제품 모드 확정 전 필수

1. **동일 golden 세트 3회 반복 완료**
   - D, A6, AO를 동일 조건으로 두 차례 더 실행한다.
   - 외부 RPD·내부 RPM/RPD baseline, 실행 세그먼트, stop reason, fallback을 매회 기록한다.
   - quota를 초과하지 않도록 여러 세션/일자로 나누고, `--continue-after-quota=true` 사용 여부를 실행 기록에 남긴다.

2. **사람 관련성 평가 추가**
   - 각 arm의 상위 5건을 질문별 1~5점으로 채점한다.
   - 정확도 100% 조건을 먼저 적용하고, 그 조건을 통과한 arm끼리 관련성 평균·recall·quota 효율을 비교한다.

3. **M6C 결과 재집계**
   - `raw_agent_candidates`, `raw_agent_selection`, `fallback_candidate_set`, `final_product_output`을 분리해 arm별로 집계한다.
   - 평균뿐 아니라 중앙값·p90·최대 Gemini 요청 수와 elapsed time을 기록한다.
   - fallback 결과를 agent 자체 성능으로 해석하지 않는다.

4. **명세 §6.4 최종 결정 반영**
   - 반복 평가와 사람 평가가 끝난 뒤에만 제품 기본 arm을 확정한다.
   - 확정 arm, 탈락 arm, 선택 근거를 `case-finder-spec.md`와 최종 보고서에 함께 기록한다.
   - 탈락 모드 코드 삭제·비활성화는 사람의 명시적 승인 후에만 한다.

5. **수용 기준 전체 실행**
   - 직접조회·미존재·환각 주입·자연어·A7 폴백·한도 소진·관련 판례 폴백·MCP 재기동·AO 상한을 실제 서버에서 확인한다.
   - `npm run check`만으로는 런타임·법제처 API·Gemini·브라우저 동작을 보증하지 않으므로, 실행 결과와 실패 로그를 별도로 남긴다.

### P1 — 선택된 arm의 운영 준비

1. **검색 회수율 개선**: 대표 실패 케이스의 검색어·도메인·후보 순위를 quota-free 로그로 재현하고, 개선 전후 golden 결과를 비교한다.
2. **도메인별 검색 계약 정리**: 판례·헌재·행정심판의 MCP 파라미터 차이를 문서화하고, 지원하지 않는 옵션이 다른 도메인으로 새지 않는지 회귀 테스트를 추가한다.
3. **AO 운영 안전성 결정**: AO를 제품으로 채택할 경우에도 wall-clock, no-new-evidence, RPD reserve, 중복 tool-call 방지를 유지하고 일일 처리량·응답시간 목표를 정한다.
4. **관측성 보강**: `logs/validation.log`와 agent 실험 로그의 보존·요약 방식을 정하고, API 키·개인정보·OC가 로그에 남지 않는지 점검한다.
5. **사용자 화면 검증**: Windows `start.bat`, `/health`, 브라우저 입력·로딩·결과 링크·오류 화면을 실제 환경에서 확인한다.

### P2 — 확정 이후 개선 후보

- 동일 질의 결과 캐시, 검색 이력, HWP/PDF 내보내기
- 인용 검증 및 조문 개정이력 표시
- 의존성 업그레이드 시 §17.2 전체 회귀 절차 자동화

## 작업 원칙

- 판례·법령 원문은 법제처 API 원문만 사용한다.
- Gemini가 후보 밖 사건번호나 조문을 만들도록 허용하지 않는다.
- 검증 실패 항목을 조용히 채우지 않고 로그에 남긴 뒤 출력에서 제외한다.
- 결과가 없으면 없다고 표시한다.
- 정확성 계약·버전 고정·제품 모드 확정 규칙을 완화하려면 먼저 사람의 승인을 받는다.
